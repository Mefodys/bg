# План: два sandbox-контейнера, два агента, два Pull Request

## Результат

Поднять два независимых Docker-контейнера. В каждом работает Codex CLI со своей
копией `Mefodys/bg`, своей веткой, тестами и журналом. Первый агент готовит PR
для формы фильтрации навыков, второй — PR для формы сравнения выбранного навыка
с навыками в других репозиториях. Агенты не мержат PR автоматически.

Это план будущей реализации: контейнеры и PR этим документом не создаются.
Визуальная спецификация двух форм — [parallel-forms-ui.md](parallel-forms-ui.md),
референс пользователя — [изображение](assets/two-sandbox-ui-reference.png).
Оба агента должны прочитать её перед реализацией UI.
Дополнительный [референс параллельного запуска](assets/parallel-launch-reference.png)
задаёт последовательность: TWO SANDBOXES → FILTER / SIMILAR → MERGE с зелёным CI.
Приведённые имена файлов и launch-скриптов — предлагаемые артефакты, а не уже
существующие команды проекта.

## Что уже есть

- Kotlin/Native CLI `bg`, сейчас собранный для macOS ARM64.
- Node.js 24 веб-сервер и интерфейс в `web/`.
- Поиск в `web/public/app.js` уже фильтрует имя, описание и все расположения
  навыка без учёта регистра. Есть фильтры категорий и состояние «нет совпадений».
- Новый макет требует поиска ещё и по полному тексту `SKILL.md` с контекстными
  сниппетами и подсветкой. Текущая реализация этого не делает.
- 30 CLI/HTTP-тестов, браузерные проверки Playwright и GitHub Actions.
- Локальные копии MPS, Koog и Android в `repositories/`; Kotlin находится
  отдельно. Эти checkout не включены в Git.
- Пока нет межрепозиторного сравнения и долговременного каталога сканов.

Таким образом, задача первого агента — улучшить и оформить существующий поиск,
а не создать ещё один дублирующий input.

## 1. Инструменты и настройки

| Где | Что установить | Для чего |
| --- | --- | --- |
| macOS-хост | Docker Desktop с Compose v2 | Два Linux-контейнера и их тома |
| macOS-хост | Git, GitHub CLI `gh` | Публикация веток/PR и чтение CI |
| macOS-хост или доверенный сервис | Codex API proxy / gateway | Авторизация агента без передачи основного API-ключа в рабочий контейнер |
| Образ агента | Linux, Git, Bash, curl, CA certificates, tar, unzip, jq | Checkout и служебные операции |
| Образ агента | Node.js 24 и npm | Веб-сервер, Codex CLI, браузерные тесты |
| Образ агента | Python 3.12 | `python3 tests/run.py` |
| Образ агента | JDK 21, Kotlin/Native 2.4.20, зависимости компилятора | Сборка Linux-бинарника `bg` |
| Образ агента | Закреплённая версия `@openai/codex` | Неинтерактивный `codex exec` |
| Образ агента | `npm ci` и headless Chromium с системными библиотеками | Существующие Playwright-тесты |

Версии образов и инструментов закрепить; не использовать плавающий `latest`.
Конкретную версию Codex CLI выбрать и проверить при подготовке образа.
Команда установки CLI — `npm install -g @openai/codex@<verified-version>`.
Образ должен проходить тест запуска компилятора, браузера и самого агента.

На Apple Silicon рекомендуемый первый вариант — Linux `amd64` через эмуляцию
Docker Desktop: он позволяет использовать Linux x86_64-дистрибутив Kotlin/Native.
Сначала проверить наличие официального архива для выбранной версии. ARM64 Linux
рассматривать отдельно после подтверждения совместимости toolchain; не считать
macOS ARM64-бинарник совместимым с Linux ARM64.

Для двух одновременно собирающих агентов предусмотреть ориентировочно 8 CPU и
16–24 ГБ памяти Docker VM, затем уточнить лимиты по пробному запуску. Эмуляция
на Apple Silicon может заметно увеличить время сборки.

## 2. Подготовительный этап: общая инфраструктура до параллельного запуска

Сделать отдельный инфраструктурный PR, проверить CI и объединить его до старта
двух задач. Оба агента должны получить один и тот же зафиксированный `BASE_SHA`
после этого merge.

### Linux-сборка

1. Адаптировать `build.sh` для macOS и Linux: определить ОС/архитектуру, выбрать
   совместимый Kotlin/Native compiler и собрать бинарник внутри контейнера.
2. Вынести платформенный код из `src/Main.kt`. Сейчас сброс `errno` использует
   Darwin `__error()`; на Linux нужен соответствующий glibc API. Например,
   отдельные `PlatformMacos.kt` и `PlatformLinux.kt` с функцией `clearErrno()`,
   которые build-скрипт подключает в зависимости от ОС.
3. Проверить также типы POSIX-констант, `stat`, `ioctl`, терминальные размеры и
   доступность остальных POSIX-вызовов. Не ограничиваться заменой одной строки.
4. Запустить все CLI/HTTP- и браузерные тесты с настоящим Linux-бинарником.
5. Добавить Linux x86_64 job в CI наряду с существующим macOS ARM64 job.
   Проверка формата бинарника должна ожидать ELF на Linux и Mach-O на macOS.
6. Привести `AGENTS.md` и README в соответствие с названиями обязательных jobs.
   Root-only пропуски тестов запрещены; контейнер и тесты работают не под root.

### Артефакты инфраструктуры

Создать:

```text
sandbox/
  Dockerfile
  compose.yml
  launch-agent.sh
  launch-all.sh
  publish-pr.sh
  tasks/
    filter.md
    similarity.md
```

`publish-pr.sh` выполняется на хосте/в доверенном publisher, а не в контейнере
с изменяемым агентом кодом. Секреты, логи и checkout не коммитить.

Сборку зависимости npm выполнять через lockfile. Chromium и зависимости
Kotlin/Native подготовить заранее, чтобы два агента не скачивали их одновременно.
Кэш компилятора должен быть отдельным для каждого агента либо заранее включённым
в образ; не давать двум компиляторам общий изменяемый `.konan`.

## 3. Изоляция двух контейнеров

| Параметр | Агент 1 | Агент 2 |
| --- | --- | --- |
| Сервис Compose | `agent-filter` | `agent-similarity` |
| Ветка | `agent/skill-filter` | `agent/skill-similarity` |
| Рабочий checkout | Отдельный том `filter-workspace` | Отдельный том `similarity-workspace` |
| Логи/результат | `filter-results` | `similarity-results` |
| Предпросмотр сайта на хосте | `127.0.0.1:4174` | `127.0.0.1:4175` |
| Задача | `sandbox/tasks/filter.md` | `sandbox/tasks/similarity.md` |

В каждом томе — полноценный независимый clone со своей `.git`. Не использовать
одну общую рабочую папку или Git worktree с общей изменяемой `.git` между
контейнерами. Задачи и опорные inventory/checkout передавать read-only.

Контейнеры запускаются под непривилегированным пользователем; не включать
`privileged`, не монтировать Docker socket, домашний каталог хоста, `~/.ssh`
или персональный `~/.codex`. Снять capabilities, включить `no-new-privileges`,
сохранить стандартный seccomp-профиль, задать CPU/RAM/PID-лимиты. Разрешить запись
только в рабочие тома, собственный кэш и временные каталоги.

Обычный Docker-контейнер — изоляция на уровне Linux, а не отдельная VM на агента.
Если нужен именно продукт Docker Sandboxes с усиленной границей изоляции,
подготовить отдельную конфигурацию по его актуальной документации; обычный
Compose не следует называть microVM sandbox.

### Важное отличие сетевого доступа к сайту

Существующий сервер слушает `127.0.0.1` внутри процесса. Docker port mapping
не сделает такой сервер доступным с хоста. В инфраструктурном этапе добавить
явную настройку bind-адреса для контейнерного предпросмотра: например,
`HOST=0.0.0.0` внутри контейнера, с публикацией только на `127.0.0.1` хоста.
По умолчанию вне контейнера сохранить loopback. Настроить допустимые Host/Origin
для портов 4174/4175, иначе текущая проверка Origin/Host отклонит браузер.
Добавить тесты этой конфигурации; не снимать проверки целиком.

Изолировать сервисы друг от друга отдельными сетями. Интернет разрешать только
для необходимых API и публичных пакетов; при строгом allowlist использовать
egress proxy/firewall. Простое наличие Docker network не является domain allowlist.

## 4. Авторизация Codex и публикация PR

### Codex

Предпочтительный вариант — отдельный доверенный API proxy/gateway вне рабочего
контейнера, который хранит OpenAI API-ключ и выдаёт каждому агенту ограниченный
доступ с бюджетом и сроком действия. Настройку Codex на gateway проверить
отдельным smoke test до выдачи задачи. Не выдумывать неподдерживаемые CLI-флаги:
использовать параметры provider/base URL из документации выбранной версии.

Не помещать ключ в Dockerfile, build arguments, репозиторий или image layers.
Не копировать персональный `auth.json`: это секрет, а проект публичный.
Официальная документация рекомендует для автоматизации API-авторизацию и
предупреждает, что репозиторный код может читать переменные окружения процесса.
Поэтому одного `CODEX_API_KEY` в окружении контейнера недостаточно для защиты
ключа от запускаемых агентом тестов и скриптов.

Агент запускается через `codex exec`. Начать с `--sandbox workspace-write`;
добавить доступ только к его собственному compiler cache. Сеть, необходимую
для API/CI, настроить явно. Не использовать устаревший `--full-auto`.
Если внутренний sandbox не позволяет выполнять браузерные тесты в Docker,
сначала исправить конфигурацию; более широкий режим допустим только после
явного выбора границы доверия и проверки внешней контейнерной изоляции.

### GitHub

Подготовить `gh auth login` на хосте или отдельный GitHub App publisher с
минимальными правами для `Mefodys/bg`: чтение/запись Contents, создание PR и
чтение Actions. Для чтения статусов/логов агенту можно выдавать отдельный
read-only credential. GitHub PR не создаётся через SSH: нужен GitHub API/`gh`.

Рекомендуемый процесс публикации:

1. Агент сохраняет коммиты в своей ветке и выдаёт patch/commit bundle и описание PR.
2. Доверенный publisher проверяет допустимую ветку, base SHA и изменённые файлы,
   применяет результат в отдельном publisher checkout и отправляет только эту ветку.
3. Publisher создаёт draft PR через `gh pr create --draft --base main --head ...`.
4. Агент получает URL PR, SHA и read-only доступ к статусам/логам для диагностики.
5. Исправления публикуются тем же способом в ту же ветку и PR.

Publisher не выполняет тесты/скрипты из присланного patch в окружении с секретами.
GitHub-ключи остаются вне контейнеров. Если вместо publisher используется PAT
в самом контейнере, явно принять риск: токен с Contents write обычно не ограничен
одной веткой. Запрет на push в `main` обеспечить ruleset/branch protection, а не
только текстом prompt. Не включать автоматический merge.

## 5. Контейнер 1: PR для формы фильтра

**Цель:** улучшить существующую форму поиска и обеспечить её полное тестирование.

Требования:

- Один заметный input «Search skills» с кнопкой очистки и доступной подписью.
- Оформление панели `Filter`, count pill `5 of 41`, компактные строки и жёлтая
  подсветка совпадений — по `parallel-forms-ui.md`.
- При вводе сразу показывать только совпавшие навыки; Enter не обязателен.
- Поиск по имени, описанию, полному `SKILL.md` и всем путям зеркальных источников,
  без учёта регистра. Показывать контекстный сниппет вокруг первого совпадения.
- Подготовить ограниченный индекс текстов на scan-сессию через проверенные API;
  не читать все манифесты заново на каждый ввод. Показывать ошибки индексации.
- Пробелы по краям игнорировать; пустая строка восстанавливает весь список.
- Поиск пересекается с выбранной категорией. Пустые секции скрываются.
- Показать count pill: число результатов / число логических навыков в текущей
  категории до текстового фильтра. Не считать зеркальные source дважды.
- Очистка восстанавливает список, сохраняя выбранную категорию.
- Различать пустой репозиторий и отсутствие совпадений; поддержать мобильный вид
  и клавиатуру. Не дублировать текущий input и не менять scanner API.

Проверки: имя/описание/body/зеркальный путь, регистр, partial match внутри слова,
whitespace, clear, category + query, safe highlight, query с HTML/regex символами,
no matches, Unicode, мобильная ширина и отсутствие JS-ошибок.

Основная область изменений: `web/public/filter.js` (новый модуль), небольшой
integration hook в `app.js`/HTML, отдельные стили и browser tests фильтра.
При необходимости — отдельный search-index API/helper в Node-сервере, согласованный
с инфраструктурными hooks; Kotlin scanner API менять не требуется.
Не менять similarity API или алгоритм второго агента.

## 6. Контейнер 2: PR для межрепозиторного сходства

**Цель:** добавить отдельную форму «Find similar skills» для выбранного навыка.
Визуально панель `Similar skills`: поле выбранного навыка, repo label,
ранжированные строки, indigo progress bars и процент справа — по UI-спецификации.

Пользователь выбирает исходный навык и другие локальные репозитории, нажимает
Compare и получает ранжированный список. Каждый результат показывает:

- процент сходства с подписью метода;
- имя навыка;
- имя репозитория, его абсолютный путь и относительный путь навыка;
- короткое описание и ссылку/кнопку просмотра source manifest;
- категорию, дополнительные source-пути и конфликтный статус.

Исходный репозиторий сравнивать с другими по каноническому realpath: алиас того
же checkout не должен попадать в результаты как «другая репа». Дублированные
target-пути нормализовать. Сканирование target checkout выполняется через `bg`;
не искать файлы вторым независимым алгоритмом в Node.js.

### Метрика первой версии

Использовать детерминированную локальную **текстовую**, а не заявленную
«семантическую» оценку. Без embeddings и дополнительных внешних API.

Рекомендуемый вариант: cosine similarity по TF-IDF-векторам полного текста
канонических `SKILL.md` после нормализации Unicode и регистра. Имена/описания
являются частью текста; не ограничивать оценку обрезанным описанием из inventory.
Определить правила токенизации и IDF в спецификации алгоритма. Корпус состоит
из исходного навыка и всех кандидатов; одинаковый вход даёт одинаковый результат.
Пустые векторы дают 0%, идентичные непустые тексты — 100%. Ограничить результат
диапазоном 0–100; сортировать по score, затем по repo/path для стабильных ties.

Предупредить в UI: это текстовое сходство, процент не является вероятностью
одинаковой функциональности. В дальнейшем embeddings можно добавить отдельно.

Разработать allowlisted API, например `POST /api/similarity`, с исходным scan ID,
идентификатором/manifest path навыка и списком target-репозиториев. Проверить
исходный навык по существующей scan-сессии. Ограничить число репозиториев,
кандидатов, размер читаемых manifest, timeout и output. Сохранять имеющиеся
Host/Origin-проверки и ограничения файлового доступа. Ошибку одной target-репы
показывать явно; не объявлять неполную выборку полным успешным сравнением.

По умолчанию сравнивать одинаковые категории; добавить явную опцию включения
test fixtures/product. Не объединять продуктовые навыки с development-зеркалами.
Макет содержит пример из исходной репы: это допустимо только через явную опцию
включения same-repo кандидатов, выключенную по умолчанию. Сам выбранный навык
в результатах не показывать. Проценты брать из алгоритма, а не из картинки.

Проверки: identical/unrelated/partial texts, empty text, Unicode, stable ties,
другие repo, realpath aliases, зеркала, категории, пропавший manifest, ошибки
target-репы, expired scan, недопустимые пути, display repo/skill/path, loading и
error states. Все данные тестов небольшие, локальные и фиксированные.

Основная область изменений: `web/similarity.mjs`, `web/public/similarity.js`,
API-hook в сервере, отдельные стили и similarity API/browser tests.

## 7. Как избежать конфликтов между двумя PR

Оба агента стартуют от одного `BASE_SHA`; запрещено переключать их на чужую ветку.
Перед стартом зафиксировать минимальные integration hooks для фильтра и detail
panel, чтобы не переписывать одним большим diff весь `app.js` или CSS.
Общую разметку/стили расширять небольшими изменениями, отдельную логику держать
в отдельных модулях. Не обещать отсутствие конфликтов: обе задачи затрагивают UI.

Агенты могут работать одновременно. Рекомендуемый порядок merge — filter PR,
затем similarity PR. Второй агент обновляет свою ветку после первого merge,
разрешает реальные конфликты и повторяет все проверки на новом SHA. Не делать
force push без отдельного разрешения; merge `main` в task-ветку допустим.

## 8. Оркестрация и цикл проверки CI

### Контракт запуска: одна задача — один sandbox

Скрипт `launch-agent.sh` должен принимать идентификатор ровно одной задачи:

```bash
bash sandbox/launch-agent.sh atlas-filter
bash sandbox/launch-agent.sh atlas-similar
```

Это будущие команды. Сейчас эти скрипты ещё не реализованы. Первая команда
запускает только сервис `agent-filter`, вторая — только `agent-similarity`.
Идентификатор определяет контейнер, checkout, ветку, prompt и журнал; неизвестный
идентификатор завершается ошибкой. Повторный запуск не должен затирать рабочую
копию или создавать второго агента в том же checkout: предложить resume/status.

Обе команды можно запустить в двух терминалах. `launch-all.sh` предоставляет
эквивалентный параллельный запуск для автоматизации: стартует оба процесса,
следит за ними независимо, собирает оба exit code и не прекращает вторую задачу
только потому, что первая завершилась или упала. Добавить команды status/stop
для конкретной задачи; остановка не удаляет рабочие тома.

На пользовательском слайде launcher называется `sbx-claude.sh`. Это название
обёртки под Claude, не стандартная команда Docker. Текущий план использует Codex
CLI и нейтральное имя `launch-agent.sh`. При выборе Claude потребуется отдельная
реализация provider/authentication; не запускать другого провайдера молча.

Задачи, показанные на слайде, включить в prompt вместе с подробной спецификацией:

> FILTER: Filter the list by words in names and descriptions. Follow the visual
> reference for counts, safe highlights, and contextual snippets; also satisfy
> the documented full-manifest and source-path search requirements.

> SIMILAR: Find similar skills. Use a deterministic local heuristic, no AI.
> Show repository identity, skill name/path, and computed similarity scores.

> MERGE: Deliver both features into main after review and authorized merging.
> Keep CI green for each PR head and for the final main revision.

«No AI» относится к алгоритму сходства в продукте: никаких embeddings/LLM API
для вычисления процентов. Писать код по этим задачам по-прежнему будут AI-агенты.

### Контроль выполнения

`launch-agent.sh` должен:

1. Проверить Docker, образ, credentials gateway/publisher и зафиксированный BASE_SHA.
2. Подготовить два checkout и две ветки; проверить, что тома не пересекаются.
3. Запустить два агента одновременно с разными prompt-файлами.
4. Сохранить JSONL-события `codex exec --json`, финальный отчёт и exit code каждого.
5. Не считать exit code 0 доказательством готовности: проверить наличие изменений,
   тестовых результатов, PR URL, head SHA и зелёных обязательных checks.
6. После публикации ждать PR CI для точного head SHA; для красного запуска дать
   агенту failed-job logs и продолжить его сессию для исправления причины.
7. При queued/in-progress ждать, при skipped/cancelled/missing/auth errors не
   выдавать статус green. Инфраструктурную ошибку отличать от ошибки кода.
8. Ограничить время/стоимость и число автоматических ремонтных циклов; например,
   три цикла, затем сохранить диагностику и запросить решение пользователя.
9. После разрешённого merge отдельно проверить CI для merge SHA в `main`.

Итоговый этап MERGE обязателен для завершения всего сценария, но не выполняется
агентами автоматически. После review и разрешения на merge сначала объединить
filter PR, обновить similarity-ветку, повторить проверки, затем объединить
similarity PR. Если итоговый `main` красный, диагностировать проблему интеграции,
подготовить отдельный repair PR и снова проверить точный SHA. Две зелёные ветки
по отдельности не гарантируют зелёный результат их объединения.

Команды проверок проекта:

```bash
bash build.sh
python3 tests/run.py
node --check web/server.mjs
node --check web/public/app.js
npm run test:web
./bg --help
./bg --version
git diff --check
```

Команды публикации/наблюдения выполняются доверенным publisher; CI-диагностика
может выполняться read-only агентом:

```bash

gh pr create --repo Mefodys/bg --draft --base main --head agent/skill-similarity --title "Compare skills across repositories" --body-file pr-body.md
gh pr checks <pr-number> --repo Mefodys/bg --watch
```

## 9. Инструкции, которые выдать агентам

Общая часть prompt на английском:

> Read AGENTS.md and the relevant specs. Work only in your assigned branch and
> checkout. Implement your assigned feature, preserve existing behavior, and add
> meaningful tests. Do not merge PRs or push to main. Run the full local build,
> strict test suite, and browser checks. Produce a patch/commit bundle and a PR
> description for the trusted publisher. Verify CI for the exact PR head SHA.
> If CI fails, inspect failing logs, fix the root cause, rerun all required
> checks, and request publication of the correction to the same PR. Report the
> verified SHA, PR URL, test results, and CI run URL. Never claim success for
> skipped tests or an unfinished CI run.

Затем добавить требования раздела 5 в `filter.md`, требования раздела 6 в
`similarity.md`, а также согласованные integration hooks и фактические команды
publisher/gateway. Не запускать агентов с одним расплывчатым prompt для обеих задач.
В оба prompt включить обязательное чтение `spec/parallel-forms-ui.md` и визуального
референса `spec/assets/two-sandbox-ui-reference.png`.

## 10. Критерии готовности

- Два независимых работающих sandbox-контейнера и две task-ветки.
- Linux- и macOS-сборки сканера проверены; сайт доступен на двух loopback-портах.
- Два отдельных draft PR с описанием поведения и проверок.
- Фильтр улучшает существующую форму, similarity работает на других checkout.
- Все обязательные CI jobs зелёные для актуального SHA каждого PR.
- После review и разрешённого merge обе функции присутствуют в `main`, и CI
  зелёный для итогового merge SHA. До этого этапа сценарий помечается как
  «PR готовы, интеграция ожидает review/merge», а не полностью завершённый.
- В рабочие контейнеры не переданы персональные SSH/Codex credentials или Docker socket.
- Пользователь получает PR URLs, инструкции предпросмотра и команду остановки
  sandbox-окружения; тома сохраняются, удаление — отдельное явное действие.
